# antwika::i18n

`src/libs/i18n/` — the machinery a message catalogue is looked up through.

## What it is for

Looking a piece of user-facing text up by a symbolic message id rather than by the English string it happens to have today.

That is the whole design decision, and everything else follows from it: because a catalogue is keyed by id, a test can assert that every locale covers **exactly** the same id set, so a missing translation fails the build instead of leaking English into a Swedish UI.

**The ids themselves are not here.**
Every module that shows text declares its own `MessageId` beside the code that shows it, writes its own catalogues, and instantiates one shared test suite over them.
This library owns `Locale`, the lookup rule, substitution, the translator and the concept the three of those are written against — and the names of the languages, which are the only strings it has to say in words of its own.

## Key types

| Header | Type | Role |
| --- | --- | --- |
| `Locale.hpp` | `Locale` | Which language a catalogue is for. |
| `MessageName.hpp` | `MessageName<Id>` | One id and the name it was declared under. |
| `MessageSet.hpp` | `MessageSet`, `nameOf` | What a module supplies, as a concept. |
| `Catalogue.hpp` | `Catalogue<Id>`, `CatalogueEntry<Id>` | One locale's messages, compiled in. |
| `Translation.hpp` | `Translation`, `TranslationOrigin` | A result, and whether it was `Exact`, a `Fallback`, or `Missing`. |
| `Lookup.hpp` | — | The resolution order, as a free function template. |
| `Substitute.hpp` | — | Filling placeholders in a looked-up message. |
| `Translator.hpp` | `Translator<Messages>` | The object an application holds. |
| `MessageId.hpp` | `MessageId` | This library's own two ids: the language names. |
| `Messages.hpp` | `Messages` | Those two ids and their catalogues, as a `MessageSet`. |

## Depends on

Nothing.

## What a module supplies

Four things, and the concept `MessageSet` is the list of them:

```cpp
namespace antwika::game
{
    enum class MessageId : std::uint16_t
    {
        ToolRoad,
        // ...
        Count,
    };

    struct Messages final
    {
        using Id = MessageId;

        static std::span<const i18n::MessageName<MessageId>> names();
        static const i18n::Catalogue<MessageId> &catalogueFor(
            i18n::Locale locale);
    };

    using Translator = i18n::Translator<Messages>;
}
```

`names()` is the list of every id there is, paired with the enumerator's own name as text.
It is one table rather than an array of ids and a `nameOf()` switch, because those were two things that had to agree with each other and a table of pairs cannot disagree with itself.

The trailing `Count` enumerator is what ties the table to the enumeration.
Each module's `Messages.cpp` carries `static_assert(kNames.size() == static_cast<std::size_t>(MessageId::Count))`, so an enumerator nobody listed is a compile error.
That is the one gap the older single central enumeration had: `kAllMessageIds` was hand-maintained, and an id missing from it was invisible to the check that read it.

The catalogue arrays are sized `kNames.size()`, so a deleted entry leaves a default-constructed one — a duplicate id with empty text, which the suite below reports rather than a shorter array nobody notices.

## Why the ids moved out, and why the guarantee survived

**A library that enumerated its consumers' strings was a library naming its consumers.**
`antwika::i18n` used to hold one `MessageId` with 239 enumerators covering `game`, `sudoku`, `companion`, `tower_defence`, `task_worker`, `atlas_editor` and `ui_demo`, plus both locales' text for all of them in one `Catalogue.cpp`.
Four files, edited by every piece of work that added a caption anywhere in the tree, and therefore the file every parallel branch collided on.

The argument for keeping them central was real and is preserved: **a catalogue is complete only against a list of everything there is**, so an id declared beside the application showing it could never be checked for.
What that argument actually requires is that the list, the catalogues and the check live *together* — not that they live in the library.
They now live together in each module, which satisfies it exactly as well.

**The check is a shared typed test suite**, `i18n::conformance::MessageSetCompleteness`, in `src/libs/i18n/tests/conformance/`.
A module instantiates it the way a backend instantiates `GfxBackendConformance` or `NetworkBackendConformance`:

```cpp
INSTANTIATE_TYPED_TEST_SUITE_P(
    Game, MessageSetCompleteness, GameMessageTraits);
```

One call site per module, no shared file to collide on, and one copy of the assertion that has to be right.
It checks that every locale's catalogue covers exactly the id set `names()` declares, with no repeats and no empty text; that a `Translator` resolves every id to `TranslationOrigin::Exact` in every locale; that `catalogueFor()` answers for each locale and falls back to the default for an unknown one; and that every id whose Swedish text equals its English one is named in the module's `sameInBothLocales()` exemption list.

That exemption list is per module too, for the reason it was ever written out: a forgotten Swedish entry looks exactly like a word that is the same in both languages, so the only way to be excused is to be named.
The suite also fails an exemption that has *since* been translated, because a stale one would excuse the next entry that goes missing.

Five ids went away rather than moving anywhere: `MenuPlayGame`, `MenuLoadReplay`, `MenuSaveReplay`, `MenuResumeGame` and `MenuLanguage` named a menu no application in the tree has, and no code outside the catalogues referenced them.
That they could sit there translated into two languages and shown by nobody is the clearest symptom of what a central enumeration costs.

**A `MessageId` is never persisted** — not in a save, not in a replay, not in a high-score file — which is why this could be done at all.
The numbering is free, so splitting one enumeration into eight and renaming `GameToolRoad` to `game::MessageId::ToolRoad` involved no schema, no version and no migration.

## How an application uses this

**A translator is injected, never reached for.**
One is constructed in `main()` and threaded down as a `const Translator &`, exactly as `log::ILogger &` and `time::IClock &` are.
There is deliberately no `defaultTranslator()`, no thread-local and no singleton: a global would be the only global state in the project, and it would let any line anywhere quietly start depending on the current language.

**There is no runtime registry either.**
A module's ids reach the library as a template argument, resolved when the program is compiled.
A registry would turn a missing translation into a runtime miss and make what a catalogue contains depend on static initialisation order.

**Which strings go through it: everything a person reads, and nothing else.**
Not a log line, not an exception message, not a JSON key, not an enumerator's name in a save file, not a replay event name, not a `ui::WidgetId`.
Those are formats and diagnostics, and a persisted name that changed to suit a caption would break the file it is written into.
A message quoting one of them takes it as a `{0}` argument, so the sentence is translated and the diagnostic inside it is not.
Notation is not prose either — `px`, `x2`, `32x16` and the `+`/`-` on a zoom button stay literals.

**The locale is either fixed in source or it is simulation state, and there is no third option.**
Text that is *measured* is reproduced: a `ui` layout is a function of the strings declared into it, and a hit-test is a function of that layout.
So the language decides what a recorded click *means*, and a run recorded in one and replayed in another resolves that click to a different widget.
An application that lays out from translated text therefore reads its locale from nowhere ambient — no environment variable and no flag, since neither is carried by a recording.
No application in the tree takes a `--locale`, and none ever will; `apps/sudoku` was the last one that did, until it grew a window, a Solve button as wide as its own label, and a grid sitting under whatever height that bar comes to.

Most applications here take the first option and fix the language at `kDefaultLocale` in `main()`, which makes changing it a source change exactly as the configured window size is.
[`game`](../apps/game.md) takes the second, because a player asked to pick a language while playing.
Its `LocaleState` owns the `Translator`, is an `ITickEventSink` registered beside the app's mode, and stages a change that lands at the tick boundary — so a press is always resolved against the layout it was made on, and the language a run was played in is reproduced the way its camera is.
Only the locale a run *starts* in is announced onto the wire, by a `LocaleSource` in `BindingSource`'s shape, since that came from the player's options file and no amount of replayed input implies it; a language picked mid-session is derived from the click, which the recording already holds.
`setLocale()` and `nameIdOf()` exist for that application and are inert for every other.

**Text a simulation decides on is decided as an id.**
`companion::Pet` picks a `Saying` and the scene words it; `atlas_editor::EditorState` holds a `StatusMessage` rather than a sentence.
Storing the words would put the active locale inside the state a replay reproduces.

## Non-obvious decisions

**Lookup is total and never throws.**
It runs while a frame is being drawn, so there is nowhere sensible for an exception to go.
The order is: the active catalogue, then the default locale, then the id's own name wrapped in exclamation marks.

**Every result says which of the three it was.**
`TranslationOrigin` is what lets a caller tell an exact hit from a fallback from a miss, so a test can insist on `Exact` while a running UI quietly accepts a fallback.
A lookup that only returned a string would make "it worked" and "it fell back" indistinguishable.

**`lookup()` takes its two catalogues as parameters** rather than reaching for them through `Messages`, which is what lets a test hand it a deliberately incomplete one and watch the fallback rule work.
`Translator` is the piece that supplies `Messages::catalogueFor(active)` and `Messages::catalogueFor(kDefaultLocale)`.

**Catalogues are compiled in rather than loaded.**
The library opens no files, which is the same position [`gfx`](gfx.md) and [`sound`](sound.md) take about images and audio.
A missing data file can therefore never change what a build says.

**Keying by id rather than by English is what makes the completeness test possible.**
Keyed by source string, a locale is "complete" only relative to whichever strings somebody remembered to extract, and the check degrades into a lint over the source.
Worse, a locale missing an entry falls through to the key, which *is* readable English prose — so a missing translation and a finished one are the same thing at runtime, nobody can see the gap, and the English original stays embedded in the calling code where a translator will never find it.

With a symbolic key the gap is a value.
Adding an eleventh message to `apps/game` and forgetting the Swedish text is a red build rather than an English label in a Swedish menu.

**`Locale` is a closed enum, not an open tag string.**
Every locale the library answers for has a catalogue compiled into it for every module, so an unrecognised tag is a parse failure at the edge in `localeFromTag()` rather than an empty catalogue in the middle.
An unknown `Locale` follows the total-lookup rule one step earlier: a module's `catalogueFor()` hands back the default locale's catalogue rather than refusing.

Adding a locale is therefore a compile error in every module at once — each `catalogueFor()` switches over `Locale` and `-Wswitch` catches the one that has no case for the new value.
That is the intended cost: a language is not half-added.

**The language names are this library's own messages**, reached through `nameIdOf()`, so a language picker reads them through the *active* translator — "English"/"Swedish" while English is on, "Engelska"/"Svenska" while Swedish is.
Showing every language under its own endonym instead is a change of catalogue data, not of code.

**The exclamation marks around a miss are deliberate.**
A gap should be something somebody notices in a screenshot, not a label that merely looks short.

## Arguments are positional

`substitute()` replaces `{0}`, `{1}` and so on by index, and `format()` does a lookup and a substitution together.
Positional rather than named, because argument *order* is the one thing a translator legitimately changes, and `{0}` lets the catalogue say so without the calling code knowing.
`game::MessageId::ToolbarZoomLevel` is the worked example: `"zoom {0}"` in both catalogues today, but nothing outside the catalogue would have to change if a language wanted the number first.

Substitution is total for the same reason lookup is.
A `{` that does not open a run of decimal digits closed by `}`, or that names an argument nobody supplied, is copied out as written, so a mis-numbered placeholder is visible in the text rather than silently blank.
A literal `{0}` is therefore not expressible; no message needs one, and an escape would be a second rule to learn for a case that has not come up.

## What is not here

There is no plural rule, no gender agreement, no date or number formatting and no locale-aware collation.
None of the strings the interface has today needs any of it, and each would be a body of rules that has to be right for every locale rather than a facility that can be added per string.

The Swedish catalogues are UTF-8 and contain `å`, `ä` and `ö`.
Whether those glyphs reach the screen is a question for whatever draws the text, not for this library, which deals only in bytes.

## The shape a module writes its set in

**A module supplies the strings and nothing else.**
`MessageTable<Id>` is the one object it writes -- its names and both locales' text, three arrays sized off the enumeration -- and `CompiledMessages<Id, Table>` is the `MessageSet` over it:

```cpp
// Messages.hpp
extern const i18n::MessageTable<MessageId> kMessageTable;

using Messages = i18n::CompiledMessages<MessageId, kMessageTable>;
using Translator = i18n::Translator<Messages>;
```

```cpp
// Messages.cpp
constexpr i18n::MessageTable<MessageId> kMessageTable{
    .names{{ ... }},
    .english{{ ... }},
    .swedish{{ ... }},
};

static_assert(
    i18n::isComplete(kMessageTable),
    "every MessageId needs a name and text in both locales");
```

That replaces a tail eight modules had a copy of: two `Catalogue` definitions, a `names()` returning the name table and a `catalogueFor()` picking between them, differing in nothing but the namespace around them and the strings above them.
The `struct Messages` shown further up this page is what those files declared by hand; it is a type alias now, and `Messages::names()` and `Messages::catalogueFor()` still mean exactly what that section says they do.

**The table is a template argument rather than a constructor argument**, because a `MessageSet` is a set of *static* functions: a `Translator` names the type and never holds an instance of it.
Declaring the table `extern const` in the header and defining it `constexpr` in the `.cpp` is what keeps the strings in one translation unit -- instantiating the template needs the table's address and never its contents, so only the module that owns the strings ever compiles them.

**The count is now right by construction, and the completeness is the `static_assert`.**
Each array is sized `messageCount<Id>`, read off the trailing `Count` enumerator, rather than by a literal length somebody kept in step with it.
So an enumerator nobody wrote a line for leaves a value-initialised entry rather than a shorter array, and a value-initialised entry -- no name, or no text -- is exactly what `isComplete()` looks for.
Deleting a Swedish string therefore fails the build before any test is run, which is what the old per-module `static_assert` on `kNames.size()` could not do: a count agreed on says nothing about whether the other locale was written.
The `MessageSetCompleteness` suite still owns everything that takes a set to see -- a repeated id, a name outside the enumeration, and the `sameInBothLocales()` exemption list -- and is still what each module instantiates.
